1 Document Loading

The pipeline starts by scanning the ./data/ directory recursively and extracting raw text from each supported file format.

.txt / .md

Read the file as UTF-8 text with errors="ignore" to handle encoding issues gracefully.

def load_txt(path: str) -> str:
    with open(path, "r", encoding="utf-8",
              errors="ignore") as f:
        return f.read()

.pdf

Extract text page-by-page using pypdf. Each page's text is joined with newlines. Scanned PDFs return empty strings (no OCR).

def load_pdf(path: str) -> str:
    reader = PdfReader(path)
    parts = []
    for page in reader.pages:
        parts.append(page.extract_text() or "")
    return "\n".join(parts)

.docx

Extract paragraph text using python-docx. Tables, headers, and footers are not captured — only the body text.

def load_docx(path: str) -> str:
    d = docx.Document(path)
    return "\n".join(
        p.text for p in d.paragraphs
    )

Dispatcher

A simple function routes each file to the correct loader by extension. Unsupported types raise a ValueError.

def load_file(path: str) -> str:
    ext = os.path.splitext(path)[1].lower()
    if ext in (".txt", ".md"):
        return load_txt(path)
    if ext == ".pdf":
        return load_pdf(path)
    if ext == ".docx":
        return load_docx(path)
    raise ValueError(f"Unsupported: {ext}")

2 Text Chunking

Raw text is split into fixed-size overlapping windows. The overlap ensures that information at boundaries is preserved in at least one chunk.

Algorithm: Sliding Window

def chunk_text(text, chunk_size=900, overlap=120):
    text = clean_text(text)       # collapse whitespace
    chunks = []
    start = 0
    while start < len(text):
        end = min(len(text), start + chunk_size)
        chunks.append(text[start:end])
        start = end - overlap     # slide back by overlap
        if end == len(text):
            break
    return chunks

Interactive Chunking Demo

Adjust the parameters and see how the document gets split. Hatched regions are overlaps.

Why These Defaults?

900
Chunk size — roughly 150-180 words. Fits inside the embedding model's 256-token window with room to spare
120
Overlap (13%) — if a sentence spans a boundary, at least one chunk will contain the full sentence

Limitation: Blind Splitting

Character-based chunking has no awareness of sentences, paragraphs, or sections. A chunk might start or end in the middle of a word:

... positive impact on the company's reve|nue growth in Q3.
                                            ^--- chunk boundary

Chunk 1 ends with: "...company's reve"
Chunk 2 starts with: "venue growth in Q3..."

P2 solves this with semantic chunking that splits at sentence boundaries based on embedding similarity.

3 Embedding

Each chunk is converted into a 384-dimensional vector that captures its semantic meaning. Similar texts produce nearby vectors in this high-dimensional space.

The Transformer Pipeline

"Retrieval augmented generation improves LLM accuracy"
              |
              v
   ┌─────────────────────┐
   │  Tokenize            │   Split into subwords: ["retrieval", "augmented", ...]
   ├─────────────────────┤
   │  6 Transformer       │   Each token builds contextual representation
   │  Layers              │   by attending to all other tokens
   ├─────────────────────┤
   │  Mean Pooling        │   Average all token vectors into one vector
   ├─────────────────────┤
   │  L2 Normalize        │   Scale to unit length (||v|| = 1.0)
   └─────────────────────┘
              |
              v
   [0.032, -0.118, 0.245, ..., 0.087]    384 floating-point numbers

Why Normalize?

When all vectors have length 1.0, the dot product between two vectors equals their cosine similarity. This means:

  • 1.0 = identical meaning
  • 0.0 = completely unrelated
  • -1.0 = opposite meaning

    documents,
    show_progress_bar=True,
    normalize_embeddings=True    # This line!
).tolist()

4 Vector Storage (ChromaDB)

ChromaDB stores four things per chunk: ID, original text, metadata, and the embedding vector. It uses an HNSW index for fast approximate nearest neighbor search.

What Gets Stored

IDDocument (text)MetadataEmbedding (384-dim)

resume.pdf::chunk_1 "...specializing in NLP, computer vision..." {"source": "resume.pdf", "chunk": 1} [0.156, -0.034, ..., 0.221]
notes.txt::chunk_0 "RAG combines retrieval with generation..." {"source": "notes.txt", "chunk": 0} [-0.089, 0.312, ..., 0.045]

The Code

# Initialize persistent storage
client = chromadb.PersistentClient(
    path="./chroma_db",
    settings=Settings(anonymized_telemetry=False)
)
col = client.get_or_create_collection(name="docs")

# Store everything in one batch call
col.add(
    ids=ids,             # ["resume.pdf::chunk_0", ...]
    documents=documents, # [chunk_text_0, chunk_text_1, ...]
    metadatas=metadatas, # [{"source": "resume.pdf", "chunk": 0}, ...]
    embeddings=embeddings # [[0.032, -0.118, ...], ...]
)

HNSW Index — How Search Works

ChromaDB uses HNSW (Hierarchical Navigable Small World) — a graph-based algorithm for fast approximate nearest neighbor search.

O(log n)
Search time — much faster than comparing every vector O(n)
SQLite
Text + metadata stored in chroma.sqlite3 on disk
Persistent
Data survives between runs — index once, query many times

At Query Time (Reverse)

# Same embedding model encodes the question
q_emb = embedder.encode(
    ["What is the candidate's experience?"],
    normalize_embeddings=True
).tolist()[0]

# HNSW graph finds nearest vectors in O(log n)
results = col.query(
    query_embeddings=[q_emb],
    n_results=4,           # top-4 nearest chunks
    include=["documents", "metadatas", "distances"]
)
